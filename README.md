# 💻 ViewHub

ViewHub — десктопное кроссплатформенное приложение для безопасной интеграции с внешними источниками данных через API, экспресс-сканирования эндпоинтов и гибкого многопоточного парсинга с инкрементальным сохранением данных в СУБД SQLite. Программа предоставляет встроенный инструмент визуализации таблиц СУБД и модульную архитектуру для сбора, обработки и аналитики данных.

---

## 🎯 Основные возможности

* **Интеграция с API и HTTPX-клиент (Функция в разработке)**: Безопасное подключение к удаленному бэкенду по HTTP-протоколу для авторизации пользователей и обмена системными данными.
* **Асинхронный экспресс-сканер (Функция в разработке)**: Универсальное высокоскоростное сканирование сетевых адресов сайтов в фоновом потоке.
* **Многопоточный парсинг товаров (`GoldenAppleParser`)**: Архитектура включает фоновые потоки `QThread`, полностью исключающие зависание GUI-интерфейса во время тяжелых сетевых операций Playwright.
* **Глубокая маскировка автоматизации (Stealth-клиент)**: Браузерный движок программно скрывает метки автоматизации в фоновом режиме (через CDP-инъекции и подмену свойств `navigator.webdriver`), имитируя поведение реального пользователя (`ru-RU`, таймзона `Europe/Moscow`). Перед каждой итерацией обхода каталога выполняется принудительная низкоуровневая очистка Origin Storage (`LocalStorage`, `IndexedDB`, кэш) для полной стерильности сессии.
* **Отказоустойчивый поштучный UPSERT**: Постраничный сбор данных с немедленной записью каждого товара на диск. Использование технологии **SQLite WAL (Write-Ahead Logging)** гарантирует максимальную скорость операций и сохранность данных при внезапном падении браузера или появлении капчи.
* **Умный контроль пагинации и дедупликации**: Перед глубоким обходом страниц парсер делает один быстрый групповой запрос `WHERE IN` к БД, выгружая словарь существующих товаров с номерами их страниц. Это позволяет **парсить только новинки**, полностью игнорировать старые карточки (`DEDUP_COLUMN = "item_id"`) и мгновенно останавливать работу при зацикливании каталога.
* **Раздвижной многозонный интерфейс с переключением слоев**: Главное окно разделено на три независимые зоны (Взаимодействие/Авторизация, Панель вывода данных, Панель логирования) с возможностью динамического изменения их размеров на лету. Встроен гибкий менеджер слоев: по кнопке **«Предпросмотр»** панель логов скрывается, а на её месте разворачивается табличный виджет.
* **Встроенный интерактивный просмотрщик БД (`DB Viewer`)**: Возможность исследовать собранные данные прямо внутри приложения без использования сторонних утилит (DBeaver, DB Browser for SQLite). Компонент динамически выгружает данные через Pandas и отрисовывает их в `QTableWidget` с автоматическим подбором ширины колонок по содержимому и заблокированным редактированием.
* **Централизованный экспорт результатов**: Мощный мастер выгрузки данных во внешние файлы Excel (`.xlsx` через движок `openpyxl`) и CSV (`.csv` с кодировкой `utf-8-sig` для корректного чтения кириллицы в Microsoft Excel). Система автоматически подставляет имя таблицы в диалоговое окно `QFileDialog` и изолирует ошибки доступа `PermissionError` (если файл открыт пользователем).

## 🔍 Детальный процесс парсинга

Парсер `GoldenAppleParser` разработан для сбора детальной информации с ресурса **Золотое Яблоко** — крупнейшей площадкой в России по продаже парфюмерии, аксессуаров для ухода за телом и товаров для дома. Сайт отличается высоким уровнем защиты от автоматизации (антибот-системы, динамический контент на Nuxt 3, Lazy-Render), поэтому парсер реализует надежный конвейер сбора данных с многоуровневой защитой от сбоев и интеллектуальным управлением пагинацией.

### Этап 1: Инициализация браузера и маскировка

1. **Запуск изолированного контекста Chromium** с постоянным профилем (`chrome_user_profile/`)
2. **Запуск в обычном режиме, а не headless.** В headless-режиме антибот отклоняет сессию (страница остаётся на `checking device`, каталог не рендерится). На Linux для этого требуется X-сервер или Xvfb
3. **Применение stealth-маскировки** через `playwright-stealth` для скрытия меток автоматизации. Применяется к **контексту**, а не к отдельной странице, поэтому распространяется и на вкладки карточек товаров
4. **Блокировка тяжелых ресурсов** (изображения, шрифты, медиа) и доменов аналитики для ускорения загрузки и экономии ресурсов
5. **Настройка локали и таймзоны** (`ru-RU`, `Europe/Moscow`) для имитации реального пользователя
6. **Очистка Origin Storage** (cookies, permissions) перед каждой сессией для полной стерильности

> **Важно про версию браузера.** В коде не задаётся фиксированный `user_agent`: Chromium сообщает свою настоящую версию. Ранее был зашит `Chrome/124`, тогда как фактически устанавливался Chromium 153 — расхождение в 29 версий легко обнаруживается и приводит к блокировке. По той же причине не используется флаг `--disable-gpu`, отключающий WebGL.

### Этап 2: Постраничный обход каталога

Парсер последовательно перебирает страницы каталога, начиная с первой:

1. **Загрузка страницы каталога** с эмуляцией скролла для активации Lazy-Render
2. **Парсинг карточек товаров** через BeautifulSoup (высокоскоростной парсер `lxml`)
3. **Извлечение базовых данных** (ID, название, бренд, URL) из карточек

### Этап 3: Интеллектуальная дедупликация

Перед глубоким обходом каждой страницы парсер выполняет **один групповой SQL-запрос** к БД:

```python
db_items_pages = manager.check_existing_items_with_pages(item_id_list)
```

Это позволяет:
- **Пропускать уже сохраненные товары** и собирать только новинки
- **Определять точку возобновления** при повторном запуске
- **Мгновенно обнаруживать зацикливание** пагинации

### Этап 4: Глубокий обход карточек

Для каждого нового товара парсер:
1. Открывает страницу товара в отдельной вкладке
2. Ждет полной загрузки контента (ждет тег `<h1>`)
3. Извлекает детальные характеристики (описание, страна происхождения, способ применения)
4. **Сразу сохраняет в БД** (построчный UPSERT с WAL-режимом)
5. Закрывает вкладку и переходит к следующему товару

### ⛔ Условия остановки парсинга

Парсер автоматически останавливается в следующих случаях:

#### 1. Ручная отмена пользователем
- Нажатие кнопки **"ОТМЕНИТЬ"** в GUI
- Флаг `_is_running` проверяется каждые 0.1 секунды в `_smart_sleep()`
- Мгновенное прерывание любых операций (загрузка страниц, паузы)

#### 2. Две пустые страницы подряд
- Если на странице нет товаров (`len(item_id_list) == 0`)
- Счетчик `empty_pages_count` увеличивается
- При достижении **2 пустых страниц** — остановка с сообщением: *"2 пустые страницы подряд. Остановка парсера."*

#### 3. Зацикливание пагинации
- Если **все товары на странице уже есть в БД** (`len(item_id_list) == old_duplicates_count`)
- Парсер проверяет: `current_page > max_page_in_db`
- Если текущая страница больше максимальной сохраненной — **зацикливание**
- Остановка с сообщением: *"Зацикливание пагинации. Остановка. Все товары сохранены."*

#### 4. Критические ошибки
- Таймаут загрузки страницы (60 секунд)
- Ошибка инициализации БД
- Сетевые ошибки (если не перехвачены)

### 🔄 Возобновление парсинга

Парсер поддерживает **продолжение с места остановки**:

1. **Автоматический пропуск дубликатов**: При повторном запуске парсер проверяет БД и пропускает уже сохраненные товары
2. **Продолжение с последней страницы**: Если на странице все товары уже сохранены, парсер переходит на следующую страницу
3. **Инкрементальное сохранение**: Каждый товар сохраняется сразу после сбора, данные не теряются при падении
4. **WAL-режим SQLite**: Гарантирует целостность данных при внезапном завершении процесса

### ⚙️ Настройки задержек

Для имитации человеческого поведения и защиты от блокировок:

- **Пауза между карточками**: 1.5–3.0 секунды (случайно)
- **Пауза после скролла каталога**: 3.0 секунды
- **Потокобезопасные паузы**: Каждая пауза разбита на шаги по 0.1 секунды с проверкой флага отмены

### 🔍 Диагностика проблем парсинга

Парсер ведёт подробный лог, потому что без него сбой на сервере выглядит как «программа зависла». Файл журнала всегда создаётся рядом с бинарником: **`logs/viewhub.log`**.

Ключевые сообщения, на которые стоит обращать внимание:

| Сообщение в логе | Значение |
|---|---|
| `Каталог браузеров Playwright: <путь>` | Каталог с Chromium найден и подставлен в `PLAYWRIGHT_BROWSERS_PATH` |
| `Обычный режим браузера — проверка устройств будет пройдена` | Графическое окружение доступно, антибот не отклонит браузер |
| `⚠️ Графического окружения нет — работаем в headless` | Не задан `DISPLAY`. Запустите Xvfb, иначе антибот может отклонить сессию |
| `Не удалось включить stealth-маскировку` | В сборку не попала папка `playwright_stealth/js`. Проверьте `collect_all('playwright_stealth')` в spec |
| `Страница переходит в режиме навигации во время чтения HTML (попытка N/5)` | Штатная гонка SPA, парсер повторяет попытку автоматически |
| `Карточки товаров (<article>) не появились` + `Диагностика страницы: http_status=...` | Содержит HTTP-статус и состояние страницы — по нему определяется причина |
| `Антибот не пускает: проверка устройства не пройдена` | Антибот отклонил устройство. Нужен другой IP-адрес или residential-прокси |
| `Сайт вернул HTTP 403/429 — запрос заблокирован защитой` | IP сервера заблокирован антиботом |

**Как читать диагностику.** Строка `Диагностика страницы` содержит HTTP-статус, URL, заголовок и первые символы текста. Пустой заголовок и `текст=СТРАНИЦА ПУСТАЯ` указывают на антибот-челлендж или сетевую ошибку; `текст=не удалось прочитать` означает, что страница была занята навигацией. HTTP-статус `200` вместе с `checking device` подтверждает, что IP чистый, но устройство не прошло проверку.

> **Полезная проверка.** Голый `curl` без User-Agent возвращает `403` практически на любом сайте с антибот-защитой — это не признак блокировки вашего IP. Проверка должна выполняться с реальным заголовком браузера: `curl -s -o /dev/null -w "%{http_code}\n" -H "User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/153.0.0.0 Safari/537.36" https://goldapple.ru/`

## 🛠️ Стек технологий

* **Язык программирования**: Python 3.11–3.14 (проверено на 3.14)
* **Автоматизация браузера**: Playwright (Chromium, эмуляция плавного скролла для Nuxt 3, подмена сетевых отпечатков и изоляция изолированных профилей)
* **Прокси-инфраструктура (Функция в разработке)**: Dante Server (SOCKS5, порт 80, фильтрация по подсетям / IP)
* **Поддерживаемые платформы сборки**: Windows и Linux (PyInstaller, режим `onedir`). Сборка должна выполняться на той же ОС, для которой создаётся бинарник
* **СУБД**: SQLite3 (Пакетная поддержка, WAL-режим транзакций, автоинкремент)
* **Графический интерфейс (GUI)**: PyQt6 (QtCore, QtWidgets, QTableView, QTableWidget)
* **Сетевое взаимодействие**: Requests, HTTPX (Асинхронные HTTP-запросы к API Django)
* **Анализ парсинга**: BeautifulSoup4 (с поддержкой высокоскоростного парсера `lxml`)
* **Аналитика данных**: Pandas (Чтение таблиц из СУБД, фильтрация данных, экспорт)
* **Менеджер зависимостей**: Poetry (v2.0+)
* **Качество кода и Тестирование**: 
  * **Ruff** (Статический анализ, проверка безопасности Bandit, автоматическое форматирование)
  * **Pytest** + **Pytest-QT** + **Pytest-Mock** + **Pytest-Cov** (Полное автоматизированное тестирование GUI, работы с БД во временных файлах и файловой системы)

## 📦 Архитектура и структура проекта

Проект спроектирован по модульному принципу со строгим соблюдением SOLID, паттерна «Стратегия» и полной изоляцией слоя баз данных и парсинга от графического интерфейса:

* **`main.py`** — Главная точка запуска приложения и инициализации глобального логгера.
* **`src/windows_pq.py`** — Сборка графического интерфейса `MainWindow`, управление слоями, сигналами и слотами Qt.
* **`src/core/paths.py`** — Единый источник правды для вычисления путей в обоих режимах (запуск из исходников и из скомпилированного бинарника). Различает каталог ресурсов (`bundle_root()`, read-only) и каталог для записи (`app_root()`), определяет путь к браузерам Playwright и гарантирует наличие каталога, доступного для записи. Содержит платформенные ветки для Windows и Linux.
* **`src/service_modules/`** — Изолированный модульный сервисный слой обработки событий интерфейса, кнопок и сигналов фоновых потоков. Разделен на специализированные модули:
  * **`auth_service.py`** (`auth_on_click` / `request_on_click`) — Интеграция с внешним Django API, обработка сессий и токенов авторизации.
  * **`parsing_service.py`** (`parsing_on_click` / `parsing_cancel_on_click`) — Управление жизненным циклом фонового потока парсера Playwright (конфигурация прокси-сессии Chromium).
  * **`scanning_service.py`** (`scanning_on_click` / `scanning_cancel_on_click`) — Управление жизненным циклом фонового потока асинхронного сканера эндпоинтов.
  * **`export_service.py`** (`parsing_export_on_click` / `parsing_db_read` / `parsing_file_save`) — Трёхэтапный конвейер выгрузки таблиц из БД в файлы с полной изоляцией побочных эффектов.
  * **`db_viewer_service.py`** (`parsing_preview_on_click` / `close_db_viewer`) — Управление встроенным просмотрщиком СУБД, динамическое монтирование/демонтаж виджетов из оперативной памяти Qt.
  * **`ui_helpers.py`** (`_update_parsing_status` / `_stop_handler`) — Вспомогательные потокобезопасные функции обратного вызова для обновления состояния UI-компонентов.
* **`src/my_exceptions/`** — Изолированный слой кастомных исключений (например, `ExceptionStopParser`), предотвращающий циклические импорты (Circular Imports).
* **`src/core/`** — Набор базовых абстрактных интерфейсов системы (ABC) и бизнес-логики.
* **`src/database/`** (`DatabaseManager`) — Сервисный слой для работы с SQLite на диске. Автоматически генерирует имена таблиц на основе конфигурации, валидирует схемы данных и накладывает индексы `UNIQUE` для дедупликации записей.
* **`src/workers/`** — Слой QThread-воркеров (`ParserWorker`, `ScannerWorker`), отвечающих за выполнение длительных блокирующих операций ввода-вывода отдельно от основного GUI-потока.

## 🧪 Тестирование и контроль качества

Сервисный слой приложения полностью покрыт автоматизированными тестами. Логика работы с базами данных изолирована через динамическое создание временных файлов БД в системных папках с помощью фикстуры `tmp_path`, а графические компоненты Qt тестируются в виртуальном контексте приложения через `qtbot`.

### 1. Запуск тестов
Для запуска всей тестовой сессии выполните:
```bash
poetry run python -m pytest
```

### 2. Проверка покрытия кода тестами (Code Coverage)
Для анализа покрытия конкретного сервисного модуля и поиска строк, не задействованных в проверках:
```bash
poetry run python -m pytest --cov=src.services --cov-report=term-missing
```

Для генерации интерактивного HTML-отчета (откройте файл `htmlcov/index.html` в браузере):
```bash
poetry run python -m pytest --cov=src.services --cov-report=html
```

### 3. Линтинг и проверка безопасности (Ruff)
Статический анализатор проекта настроен на строгий контроль безопасности (Bandit) в боевом коде, при этом тесты автоматически изолированы через правила `per-file-ignores` в файле `pyproject.toml` (пропускаются ложные срабатывания на мок-токены `S105` и `assert`-конструкции `S001`).
```bash
poetry run ruff check
```

## 🚀 Установка и запуск

### 1. Подготовка репозитория
```bash
git clone https://github.com/burmspb-code/ViewHub.git
cd ViewHub
```

### 2. Установка зависимостей и системных библиотек

Для автоматического управления виртуальным окружением используется **Poetry**.

* **ВАЖНО для пользователей Linux (Ubuntu / Debian):**
  Перед установкой проекта необходимо обновить системные пакеты и установить системные зависимости, которые требует движок Playwright (библиотеки шрифтов, графического сервера и аудио):
  ```bash
  sudo apt update
  # Автоматическая установка системных зависимостей для Playwright
  poetry run playwright install-deps
  ```
  *(Если вы настраиваете чистый Linux-сервер без графической оболочки (headless VPS), эта команда установит минимальный набор библиотек, необходимых для работы браузера в фоновом режиме).*

* **Локальная разработка (Запуск из исходного кода):**
  По умолчанию Playwright устанавливает бинарные файлы браузеров в глобальный системный кэш пользователя. Для обычной отладки выполните:
  ```bash
  poetry install
  poetry run playwright install chromium
  ```

* **Подготовка к автономной сборке (необязательно):**
  Если в `viewhub.spec` выставлен `BUNDLE_BROWSERS = True`, браузер нужно скачать внутрь рабочей папки проекта, чтобы сборщик забрал его с собой. При `BUNDLE_BROWSERS = False` (по умолчанию) шаг не нужен — приложение возьмёт Chromium из системного кэша Playwright.
  
  * **В Linux / macOS (Bash/Zsh):**
    ```bash
    export PLAYWRIGHT_BROWSERS_PATH="pw-browsers"
    poetry run playwright install chromium
    ```
  * **В Windows (PowerShell):**
    ```powershell
    $env:PLAYWRIGHT_BROWSERS_PATH="pw-browsers"
    poetry run playwright install chromium
    ```
  
  *(Если собираете под Linux и нужно, чтобы бинарник был полностью автономным, выполняйте эту команду на Linux-машине: Chromium платформенно-зависим.)*

### 3. Настройка окружения

## 📦 Сборка в исполняемый файл (PyInstaller)

Проект собирается через PyInstaller в **директорию** (режим `onedir`): результатом является папка `dist/viewhub/` с исполняемым файлом и всеми зависимостями внутри. Выбран именно этот режим, а не `onefile`, потому что распаковка ~550 МБ в `/tmp` при каждом запуске заметно замедляет старт.

Сборка одинаково поддерживается для **двух ОС — Linux и Windows**.

> ⚠️ **Собирать нужно на той же ОС, для которой делаете бинарник.** Chromium платформенно-зависим: собранный на Windows Chromium не запустится в Linux-сборке и наоборот. Установка `playwright install chromium` должна выполняться на той же машине, что и компиляция.

### Режим сборки: `onedir` против `onefile`

| | `onedir` (используется) | `onefile` |
|---|---|---|
| Структура | папка `dist/viewhub/` | один файл ~550 МБ |
| Скорость запуска | **мгновенно** | распаковка ~550 МБ в `/tmp` при каждом старте |
| Перенос на сервер | копируется вся папка целиком | копируется один файл |

При `BUNDLE_BROWSERS = False` (по умолчанию) размер сборки — около 120 МБ, поскольку Chromium не упаковывается внутрь.

### ⚙️ Ключевые настройки `viewhub.spec`

Все настройки сборки собраны в начале файла — их можно менять без правки логики приложения:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `BUNDLE_BROWSERS` | `False` | Упаковывать ли Chromium внутрь сборки. `False` — берётся из кэша Playwright на сервере, сборка ~120 МБ. `True` — автономный бинарник ~550 МБ |
| `CONSOLE_MODE` | `True` | Вывод диагностики в терминал. **Критично для отладки на сервере** |
| `USE_UPX` | `False` | UPX-сжатие. Для сборки с Chromium и Node даёт малый выигрыш, но замедляет сборку и может повредить крупные бинарники |
| `BROWSERS_DEST` | `"pw-browsers"` | Куда упаковывается Chromium при `BUNDLE_BROWSERS = True`. Значение должно совпадать с `src.core.paths.BROWSERS_DIR_NAME` |

### Инструкция по сборке для Linux

1. Установите системные зависимости и браузер:
   ```bash
   sudo apt update
   poetry run playwright install-deps chromium
   poetry run playwright install chromium
   ```

2. Запустите компиляцию:
   ```bash
   poetry run pyinstaller viewhub.spec --clean --noconfirm
   ```

3. Результат: папка **`dist/viewhub/`** с бинарником `viewhub`.

4. Убедитесь, что доступен графический стек (см. раздел ниже про Xvfb), затем запустите:
   ```bash
   ./dist/viewhub/viewhub
   ```

### Инструкция по сборке для Windows

1. Установите браузер:
   ```powershell
   poetry install
   poetry run playwright install chromium
   ```

2. Запустите компиляцию:
   ```powershell
   poetry run pyinstaller viewhub.spec --clean --noconfirm
   ```

3. Результат: папка **`dist\viewhub\`** с исполняемым файлом `viewhub.exe`.

4. Запуск:

### 🖥 Обязательное условие на Linux: графическое окружение

Парсер **намеренно запускает обычный браузер, а не headless**. В headless-режиме антибот-система Золотого Яблока отклоняет сессию: страница остаётся на этапе `Gold Apple — checking device`, каталог не отрисовывается, и парсер завершается с ошибкой «данные не обнаружены».

На Linux обычный браузер требует X-сервера. Если графического окружения нет, используйте **Xvfb**:

```bash
# Установить виртуальный дисплей
sudo apt install -y xvfb

# Запустить его и задать DISPLAY
Xvfb :99 -screen 0 1366x768x24 &
export DISPLAY=:99
```

На Windows такой настройки не требуется — обычный режим браузера работает из коробки.

Если `DISPLAY` не задан, парсер переходит в headless и выводит предупреждение в лог и GUI. В этом случае при запуске вы увидите:

```
⚠️ Графического окружения нет — работаем в headless, антибот может отклонить.
```

**Постоянная настройка для systemd-сервиса.** Чтобы не задавать `DISPLAY` вручную при каждом запуске, пропишите виртуальный дисплей в сервисе:

```ini
[Service]
Environment=DISPLAY=:99
ExecStartPre=/usr/bin/Xvfb :99 -screen 0 1366x768x24
ExecStart=/root/ViewHub/dist/viewhub/viewhub
```

### 🧪 Эксперимент: режим отрисовки браузера

Переменная `GOLDAPPLE_HEADLESS` переключает режим отрисовки **без правки кода и без пересборки**:

| Значение | Режим |
|---|---|
| не задана | автоопределение (рекомендуется) |
| `1`, `true`, `yes`, `on` | принудительно **headless** — минимальное потребление ресурсов |
| `0`, `false`, `no`, `off` | принудительно обычный браузер |

**PowerShell:**
```powershell
$env:GOLDAPPLE_HEADLESS="1"
.\dist\viewhub\viewhub.exe
```

**Linux (Bash):**
```bash
export GOLDAPPLE_HEADLESS=1
./dist/viewhub/viewhub
```

Автоопределение работает так: на Linux обычному режиму требуется X-сервер, поэтому при отсутствии `DISPLAY` включается headless; на Windows обычный режим выбирается всегда, так как X-сервер не нужен.

> ⚠️ **Ожидайте отказ антибота.** В headless-режиме проверка устройств Золотого Яблока, как правило, не проходит: страница остаётся на `Gold Apple — checking device`, каталог не отрисовывается, парсер завершается с «данные не обнаружены». Эксперимент полезен, чтобы **измерить** это на конкретной машине: если headless заработает, ресурсы VPS можно снижать существенно.

Активный режим всегда виден в логе:
```
Режим отрисовки: headless (GOLDAPPLE_HEADLESS=1)
```

### ⚙️ Внутренняя механика сборки (Для разработчиков):

* **Режим `onedir`:** Блок `COLLECT` в `viewhub.spec` размещает все бинарники и данные в `dist/viewhub/_internal/`, а `EXE` содержит только загрузчик и точку входа.
* **Драйвер Playwright:** Подключается явно через `collect_all('playwright')`. Драйвер — это Node.js-бинарник, который Playwright ищет по пути `<MEIPASS>/playwright/driver/node`. Без явного включения он может не попасть в сборку.
* **Маскировка `playwright_stealth`:** Подключается через `collect_all('playwright_stealth')`. Библиотека читает JS-файлы из `playwright_stealth/js/` **в момент импорта** (`stealth.py`, `from_file()`). Если папка не попала в сборку, маскировка отключается целиком, а `navigator.webdriver` остаётся равным `true` — сайт начинает отдавать антибот-челлендж.
* **Ресурсы и иконка:** `src/core/assets/` упаковывается по тому же пути, который читает `src/core/resources.py`.
* **Динамические пути (`sys.frozen`):** Все вычисления путей централизованы в модуле `src/core/paths.py`. Функция `bundle_root()` возвращает каталог ресурсов сборки (`_internal`), а `app_root()` — папку рядом с бинарником, куда приложение может писать (БД, профиль, логи). Такой подход одинаково корректен для `onedir` и `onefile`.
* **Путь к браузерам:** Определяется в `src/core/paths.py` в следующем порядке: переменная `PLAYWRIGHT_BROWSERS_PATH` из `.env` → упакованная папка `pw-browsers` → системный кэш текущей ОС. Каталог проверяется на существование **и на непустоту**, поскольку пустая папка хуже её отсутствия: Playwright получил бы валидный на вид путь и упал бы с невнятной ошибкой.
